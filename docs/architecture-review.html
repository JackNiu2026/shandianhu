二、架构亮点（做得好的地方）

亮点monorepo + shared 层设计合理

pnpm workspace + @lightning-tiger/shared 包统一管理跨端类型（Teacher/Prefs/MBTI）、常量（科目/学段/预算/题目）、工具函数（MBTI 计分/老师筛选），避免 mobile 与 admin 双份维护。Next.js 用 transpilePackages、Taro 用 compile.include 分别正确处理了共享包的编译。

亮点Next.js App Router 分层清晰

使用 Route Groups (auth)/(dashboard) 分离登录态布局，API 路由按资源域组织（auth/teachers/parents/bookings/reviews/memberships/finance/content/dashboard/public），RESTful 程度高。middleware 统一处理页面守卫 + API 鉴权 + 动态 CORS。

亮点Dockerfile 多阶段构建规范

三阶段（deps → builder → runner）+ output: standalone 最小化镜像体积；runner 用非 root 用户 nextjs:1001；启动时自动 prisma migrate deploy；healthcheck 落到真实 API 端点。这些是生产级实践。

亮点认证与安全配置到位

JWT + httpOnly Cookie + sameSite=lax + 生产环境 secure:true；middleware 区分 admin/parent 角色，管理端 API 拒绝家长 token；Nginx 强制 HTTPS + HSTS + X-Frame-Options DENY；CORS 基于 Origin 白名单动态匹配（解决了 * + credentials 的规范冲突）。

亮点设计系统跨端统一

Neo-brutalism 风格（border-2 + 硬阴影）+ 语义色变量（ink/growth/action/surface）在 C 端 SCSS 与 B 端 Tailwind @theme 中保持一致值，品牌识别度强。

三、问题清单（按严重程度分级）

P0 — 严重问题（必须修复，影响数据正确性 / 工程协作）

P0-1 · Message 模型外键设计缺陷，teacher 发消息会违反约束packages/admin/prisma/schema.prisma:175-192

问题：Message.senderId 和 receiverId 都是 String 且都通过 @relation 指向 Parent 表，但 senderRole 注释为 parent | teacher。一旦老师发消息，senderId 填 teacher.id 会因外键不存在而直接报错。

影响：聊天功能在老师端不可用，或被迫绕开外键（删 relation），数据完整性丢失。

修复方案（二选一）：

// 方案 A：多态关联（推荐，改动小）
model Message {
  ...
  senderId     String
  senderRole   String   // parent | teacher | admin
  receiverId   String
  receiverRole String
  // 删除 sender / receiver 两个 @relation，应用层校验
  @@index([senderId, senderRole])
  @@index([receiverId, receiverRole])
}

// 方案 B：显式分表，强类型
model Message {
  ...
  senderParentId   String?  @relation("MessageSenderParent", fields: [senderParentId], references: [id])
  senderTeacherId  String?  @relation("MessageSenderTeacher", fields: [senderTeacherId], references: [id])
  receiverParentId String?  @relation("MessageReceiverParent", fields: [receiverParentId], references: [id])
  // 应用层保证 sender 二选一非空
}
P0-2 · mobile 嵌套独立 git 仓库，与根仓库双轨追踪packages/mobile/.git/

问题：packages/mobile/ 下存在独立 .git（仅 1 个 "Initial Commit"），但根仓库 git ls-files packages/mobile/ 同时也追踪了 mobile 的文件。根目录无 .gitmodules，说明这不是合法 submodule，而是"嵌套 git 仓库"——典型的 monorepo 反模式。

影响：mobile 内的 git commit/push 只进 mobile 仓库，根仓库历史与 mobile 仓库历史永久不同步；CI 拉根仓库时 mobile 是普通文件，拉 mobile 仓库时看不到 admin/shared；协作时极易丢失提交。

修复方案：

# 1. 备份 mobile 的提交（如有需要）
git -C packages/mobile log --oneline  # 记录 commit hash

# 2. 删除嵌套的 .git（mobile 文件已被根仓库追踪，不会丢代码）
rm -rf packages/mobile/.git

# 3. 在根仓库一次性提交
git add packages/mobile/
git commit -m "chore: 合并 mobile 子仓库到 monorepo"

# 4. 若 mobile 有远程仓库需要保留历史，用 git subtree 合并：
#    git subtree add --prefix=packages/mobile <mobile-remote-url> main

P1 — 重要问题（建议尽快修复，影响可维护性 / 类型安全）

P1-1 · React 版本不一致，shared 被两端共用存在隐患packages/admin/package.json:24 · packages/mobile/package.json:23 · README.md:9

问题：admin 用 react@^19.0.0，mobile 用 react@^18.0.0，README 写的却是"React 18"。next.config.ts 里用 webpack alias 强制 react 指向 admin/node_modules/react，这本身就是版本冲突的临时补丁。shared 包虽不直接依赖 react，但导出的类型若涉及 React 类型（如 hooks），两端 React 类型定义不一致会埋雷。

影响：shared 若将来导出 hooks/组件，两端 React 类型不兼容会导致类型报错；运行时可能因 React 实例多份导致 context 失效。

修复方案：统一到 React 18（Taro 4 对 19 支持不明，且 18 是 LTS）。修改 packages/admin/package.json：

"react": "^18.3.1",
"react-dom": "^18.3.1",
"@types/react": "^18.3.0",
"@types/react-dom": "^18.3.0"

同步更新 README，删除 next.config.ts 里的 react alias 补丁。

P1-2 · Prisma 大量字段用 String 存 JSON，丢失类型与查询能力packages/admin/prisma/schema.prisma:28-39, 64-66

问题：Teacher.grades/tags/slots/checks、Parent.prefs/mbtiResult/likedTeachers 都用 String 存 JSON 字符串，注释写"JSON string of array"。Prisma 原生支持 Json 类型，PostgreSQL 也有 jsonb，能直接查询/索引。

影响：应用层每次都要 JSON.parse/JSON.stringify，易出错；无法用 Prisma 查询 JSON 内字段（如"找所有支持高中的老师"）；数据库层无 schema 约束。

修复方案：

// 简单 JSON 字段直接改 Json 类型
grades  Json   // ["小学","初中"]
tags    Json   // ["耐心","985"]
slots   Json   // ["周一 19:00", ...]
prefs   Json?
likedTeachers Json @default("[]")

// 高频查询的字段拆关联表（如 likedTeachers）
model LikedTeacher {
  parentId  String
  teacherId String
  parent    Parent   @relation(fields: [parentId], references: [id])
  teacher   Teacher  @relation(fields: [teacherId], references: [id])
  createdAt DateTime @default(now())
  @@id([parentId, teacherId])
}
P1-3 · 状态/角色字段用 String + 注释，未用 enumschema.prisma: 17,40,61,68,88,105,122,135,161

问题：AdminUser.role、Teacher.status、Booking.status、Review.status、Order.status/type、Withdrawal.status 等全部用 String + 行内注释枚举值。数据库层不约束合法值，应用层任意写错都不报错。

修复方案：用 Prisma enum（PostgreSQL 原生支持）：

enum AdminRole { superadmin editor }
enum TeacherStatus { active pending blocked }
enum BookingStatus { pending confirmed completed cancelled }
enum ReviewStatus { pending approved rejected }
enum OrderType { membership lesson tip }
enum OrderStatus { pending paid cancelled refunded }

model Teacher {
  ...
  status TeacherStatus @default(pending)
}

迁移后应用层删除手写的联合类型，直接用 Prisma 生成的类型。

P1-4 · 全项目零测试，含真实交易逻辑全仓库无 *.test.ts / *.spec.ts

问题：项目有订单、会员、提现、预约状态流转等涉及金钱的逻辑，但没有任何单元测试/集成测试。CI（.github/workflows/ci.yml）只能跑 typecheck/lint/build，无法防止回归。

修复方案：优先补 3 类测试：

  • shared/utils 工具函数（MBTI 计分、match 筛选）— 纯函数，最容易测，用 Vitest。
  • API 路由（订单状态流转、提现审批、预约确认）— 用 Vitest + supertest 或 Next.js route testing。
  • Prisma 查询（关键报表统计：finance/stats、dashboard/stats）— 用测试数据库隔离。
# packages/admin 加 vitest
pnpm --filter admin add -D vitest @vitest/coverage-v8
# package.json: "test": "vitest run"
P1-5 · admin 同时存在 App Router 和 Pages Routerpackages/admin/src/pages/_error.tsx

问题：项目主体用 App Router（src/app/），但残留 src/pages/_error.tsx。Next.js 15 中两套路由系统共存时，Pages Router 的 _error.tsx 只处理 Pages Router 路由的错误，App Router 的错误应通过 app/error.tsx 捕获。

修复方案：删除 src/pages/ 目录，在 src/app/error.tsx 和 src/app/global-error.tsx 实现错误边界。

P2 — 改进建议（提升工程质量，非阻塞）

P2-1 · shared 空壳目录未导出packages/shared/api/ · packages/shared/hooks/ · packages/shared/index.ts

问题：shared 有 api/ 和 hooks/ 目录（迁移文档说是"预留空壳"），但 index.ts 没有导出它们。要么是死代码，要么是未完成的占位。

修复：若暂不用就删除目录；若要保留，在 index.ts 导出并加注释说明用途。

P2-2 · ESLint 关闭了 no-explicit-anypackages/admin/eslint.config.mjs:17

问题："@typescript-eslint/no-explicit-any": "off" 放任 any 使用，削弱了 TypeScript 的类型保障。

修复：改为 "warn"，逐步清理现有 any，再升级为 "error"。优先用 unknown 替代 any。

P2-3 · Dockerfile 复制了不需要的 mobile package.jsonpackages/admin/Dockerfile:15

问题：Stage 1 复制了 packages/mobile/package.json，但 admin 镜像构建根本不用 mobile。这会让 pnpm install --frozen-lockfile 安装 mobile 的全部依赖（Taro/webpack 等），白白增大构建时间和中间层体积。

修复：删除 COPY packages/mobile/package.json ./packages/mobile/ 这一行；或在 .npmrc 里配置 --filter admin... 只装 admin 子树。

P2-4 · Nginx 静态资源代理方式低效nginx.conf:40-44

问题：location /_next/static/ 用 proxy_pass 转发到 Next.js，应由 Nginx 直接服务静态文件（CDN/本地文件）。且 proxy_cache_valid 200 1y 没有定义对应的 proxy_cache_path，缓存不会生效。

修复：构建时把 .next/static 挂载到 Nginx 容器，直接 alias /app/.next/static/;；或用 CDN 回源。删除无效的 proxy_cache_valid。

P2-5 · db:push 与 db:migrate 并存，开发流程不统一package.json:16-18 · README.md:47-49

问题：根 package.json 同时提供 db:push（开发期直接同步 schema，不生成迁移）和 db:migrate（生产部署迁移）。两者混用会导致迁移历史不一致——开发用 push 改了 schema，生产 migrate deploy 时缺迁移文件。

修复：统一用 prisma migrate dev 开发（每次改 schema 生成迁移文件，进版本控制），prisma migrate deploy 生产部署。删除 db:push 脚本，仅在 seed 场景保留 push。

P2-6 · 文档与实现不同步docs/b-end-admin-panel-implementation.md:54,387

问题：B 端实现文档写"当前无后端，内存 mock + Promise 封装"，但实际 lib/data.ts 已是 fetch('/api/...') 调真实 API，Prisma schema 也已落地。文档严重滞后。

修复：更新文档反映真实状态，或在过时文档顶部加 > ⚠ 已过时，仅作历史参考 标注。

总体结论

项目架构骨架科学合理——pnpm monorepo、Next.js App Router、Taro 跨端、Prisma + PostgreSQL、Docker 多阶段构建、JWT + httpOnly Cookie 鉴权，这些都是 2025 年的主流正确选型，部署与安全配置达到生产级。

主要短板集中在数据建模和工程协作：Prisma schema 大量用 String 存 JSON、状态字段未用 enum、Message 模型外键设计有缺陷；mobile 嵌套独立 git 仓库是协作隐患；全项目零测试对含交易逻辑的平台风险偏高。

建议优先级：先修 P0（Message 外键 + mobile git 合并）→ 再修 P1（React 版本统一 + Prisma 类型化 + 补测试）→ P2 按需优化。完成 P0/P1 后，项目可达到"可放心迭代的中型生产项目"水准。
